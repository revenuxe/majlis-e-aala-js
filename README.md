Assume that a significant number of customers are not technically experienced.

A customer must NEVER need to understand how the application works before they can request catering.

Design the primary booking journey so that a first-time user can complete it without instructions.

The main journey must contain only 6 conceptual steps:

1. Occasion

2. Date & Guests

3. Package or Custom Menu

4. Food Selection

5. Optional Services

6. Review & Contact Details

Use one clear question per screen whenever possible.

Never show a large complicated form.

Never ask for information earlier than it is needed.

Use plain customer-friendly language.

Avoid technical or restaurant-industry terminology.

Each screen must have ONE obvious primary action.

Always show:

Back

Current progress

Primary Continue action

Example progress:

Date & Guests

Keep progress visually simple.

Do not require account creation before a catering request.

GUEST CHECKOUT IS REQUIRED.

BACK BUTTON SAFETY:

Going backward must NEVER erase previous selections.

Customers must be able to change:

occasion

guest count

package

food

services

without restarting the booking.

STICKY MOBILE CTA:

On every booking step use a large bottom CTA above the bottom safe area:

Continue

or contextually:

See Packages

Continue to Menu

Review My Catering

Confirm Catering Request

Never hide the main action at the bottom of a long page.

LARGE TOUCH TARGETS:

All important controls must be at least 44px tall.

Do not use tiny radio buttons.

Convert important selections into large tappable cards.

PRICE TRANSPARENCY:

Whenever possible show pricing immediately.

Example:

Premium Package

₹699 / guest

150 guests

Estimated Food Total

₹1,04,850

Avoid surprising the customer with pricing only at the final step.

If pricing cannot be guaranteed, clearly label:

Estimated Price

Final price will be confirmed by our catering team.

NO DEAD ENDS:

Every screen must make it obvious what the customer should do next.

If no menu item is selected:

Explain what is required.

If a date is unavailable:

Suggest contacting Majlise Aala instead of simply blocking the customer.

ACCESSIBILITY:

Use readable font sizes.

Body text should generally not be smaller than 14–16px.

Maintain strong contrast.

Do not rely only on icons.

Always accompany unfamiliar icons with text.

OLDER USER FRIENDLINESS:

Avoid swipe-only functionality for essential actions.

Horizontal carousels may be used for discovery, but critical choices must also be accessible without requiring the user to discover a swipe gesture.

Do not use hidden gestures.

Do not use tiny dropdowns.

Prefer obvious cards, buttons, +/- quantity selectors and date pickers.

FINAL UX TEST:

Before considering any booking screen complete, ask:

"If a customer who rarely uses apps opened this screen, would they immediately know what to tap next?"

If the answer is not clearly yes, simplify the screen.

The user should be capable of completing a catering request in approximately 2–4 minutes.
